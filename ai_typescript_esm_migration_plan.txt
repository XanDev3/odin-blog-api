# TypeScript + ES Modules Migration Plan for Odin Blog API
Generated: January 9, 2026

## Overview

This migration will incrementally convert the Odin Blog API from JavaScript with CommonJS to TypeScript with ES modules in a src/ directory structure. The approach uses small, manageable steps (maximum ~20 changes per step) to ensure each phase is easily reviewable and testable. The plan establishes TypeScript foundation, restructures to src/, transitions to ES modules, types all files, enables strict mode, then systematically fixes strict errors file-by-file.

## Further Considerations

### 1. Source directory impact on static files
The public/ and views/ folders remain at root, but src/app.ts uses __dirname which now points to dist/ in production. Verify path.join(__dirname, '../public') and path.join(__dirname, '../views') work correctly, or use process.cwd() instead for root-relative paths.

### 2. Declaration merging namespace conflicts
Using declaration merging in src/types/express.d.ts is clean but can conflict if other libraries also augment Express types. If you encounter "Property user is not compatible" errors, switch to generic parameters: Request<ParamsDictionary, any, any, ParsedQs, { user?: IUserDocument }>.

### 3. Environment variable type safety
Consider creating src/types/environment.d.ts to augment NodeJS.ProcessEnv with your required env vars (MONGODB_URI, JWT_SECRET, PORT, etc.) for compile-time validation that all required environment variables are typed.

### 4. Optional: Automated OpenAPI generation
After migration is complete and stable, investigate tsoa (NOT @nestjs/swagger) for Express-compatible automated OpenAPI generation from TypeScript decorators. This would require refactoring controllers to use decorators but maintains Express architecture and keeps spec synchronized with types. Current static spec works fine - only pursue if you want automated sync.
